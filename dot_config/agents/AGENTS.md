# 全局工作约定

编码 agent 的用户级指令文件，对所有工作目录生效。仓库内自带 `AGENTS.md` 优先级更高，冲突时以仓库为准。
只写仓库里读不到的东西：不列目录结构，不抄 package.json / README 已有内容。
pi 与 dsh 通过软链共用本文件：这里只写两者都成立的通用条款，工具专有的命令和路径放项目级文件。

## 交流

- 中文回答；代码、命令、路径、报错原文保持原样，不翻译。
- 先给答案或先动手，再补必要说明。不复述我已知的内容，不写开场白和"以上就是全部"式收尾。
- 提问一次问清楚，不要边做边反复打断；能自己读代码/跑命令确认的，就不要问。
- 不确定的事实去读代码或探测，不凭印象断言；确实无法验证时直说无法验证。
- 对我的方案有异议，先明确说同意或不同意并给理由，再说你改了什么。
- 报错给四样：命令、关键错误行、原因判断、下一步。不要贴整段日志。

## 工作方式

- 先读后改：修改前读够相关代码（含调用方与相邻文件），确认现有风格与抽象，不凭文件名猜实现。
- 改动聚焦：只解决当前问题，不顺手重构、不格式化无关文件。
- 复用优先：新增文件或依赖前先搜现有实现。
- 不确定某工具、命令、包是否存在，先探测（`command -v`、版本）。
- 长时间或可能卡住的命令加超时；交互式命令（`vim`、`less`、`top`）改用非交互等价写法。
- 编辑用精确替换，只动需要改的行；不要整文件重写。
- 不新增依赖，除非必要；新增时说明现有方案为何不够。

## 边界

可以自行做：读文件与搜索、查看 `git status/diff/log`、跑 lint / 类型检查 / 单个测试文件、在 `/tmp` 写临时脚本。

必须先确认：安装或升级依赖、删除文件或目录、`git commit` / `push` / 建分支 / 改 remote、改全局配置或 shell 启动文件、批量重写文件、执行迁移或覆盖现有数据、动 `~/.pi`、`~/.dsh` 这类 agent 配置目录。

绝不执行：`git add -A`、`git add .`、`git reset --hard`、`git checkout .`、`git clean -fd`、`git stash`、`git commit --no-verify`、`git push --force`。多个 agent 可能在同一仓库并行工作，上面这些会毁掉别人的改动。提交时只 `git add` 自己改过的具体路径，提交前用 `git status` 确认暂存范围。

## 代码风格

- 跟随目标文件与仓库既有风格：缩进、引号、命名、目录结构以邻居文件为准；冲突时以仓库的 linter / formatter / `.editorconfig` 为准。
- 命名直白达意，避免 `data`、`tmp`、`helper2` 这类占位名。
- 注释只写"为什么"，不写"是什么"；不留被注释掉的死代码。
- 错误处理显式：不要空 `catch`，不要把异常吞成静默 `null`；面向用户的错误信息要说清怎么修。
- 不留调试残留（`print` / `console.log` / `dbg!` / 临时 sleep），提交前清掉。
- 类型能收紧就收紧，避免 `any`、`interface{}`、无类型字典当默认逃逸口。
- 不要为了绕过类型错误而删除或降级代码——升级依赖或修类型。
- 看起来"没用"的代码可能是故意的，删除前先问。
- 新增公开函数或模块时，同步更新类型声明与调用点，不留悬空引用。

## 安全与隐私

- 不读取、不打印、不写入、不提交密钥类内容：`~/.ssh`、`~/.gnupg`、agent 的 `auth.json` 与凭据文件、`.env`、`*token*`、`*credential*`、`*.pem`。需要时只用环境变量名，不取值。
- 不把本机文件内容发到外部服务；联网搜索只用于公开资料，不夹带私有代码或路径。
- 目录里看到的隐私信息（真实姓名、路径、内网地址、key）不写进提交、文档或示例。

## 收尾

- 改完给出：改了哪些文件、关键变更点、如何验证（可复制执行的命令）。
- 能跑就自己跑一遍（仓库的构建 / 测试 / lint / 类型检查），说明实际结果；跑不了就说明原因。
- 未完成的部分和已知风险明说，不要用"应该没问题"收尾。
